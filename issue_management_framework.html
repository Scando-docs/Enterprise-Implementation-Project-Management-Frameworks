Issue Management Framework

Systematic Issue Resolution | Standard Implementation Methodology

1. Overview & Objectives

While risks are potential future events, issues are realities currently impacting the project. This framework establishes clear Service Level Agreements (SLAs), strict escalation paths, and categorized routing to ensure the implementation team and client stakeholders resolve roadblocks rapidly—especially during critical phases like Data Migration and UAT—without threatening the project timeline.

2. Issue Classification & Service Level Agreements (SLAs)

To ensure alignment between Client Process Owners and the Implementation Team, issues must be categorized and prioritized upon submission.

Priority Definition (System Context) Target Response Target Resolution
Critical System down (Go-Live phase), complete halt of UAT, or major financial data corruption. Prevents core project progress. 4 Hours 24 Hours (Requires RCA)
High Major module (e.g., Procurement) workflow broken, severely impacting critical deliverables. No workaround exists. 8 Hours 3 Working Days
Medium Sub-component defect, minor report formatting issue, or manageable data mapping error. Workaround available. 24 Hours 10 Working Days
Low Cosmetic UI issues, non-critical translation updates, or future enhancement requests. 48 Hours Best Effort (Next Sprint)

3. The Issue Lifecycle Workflow

1

Identification & Logging (Status: Received)

Any project team member (e.g., Client Key Users) identifies an issue and logs it in the centralized Project Issue Tracker. Must include: Category (Technical, Functional, Data), Steps to Reproduce, and tentative Priority.

2

Triage & Assignment (Status: Open)

The Project Management Team reviews the issue within the Response Target, validates the priority, and assigns an Issue Owner (e.g., Lead Functional Consultant, Client IT Lead).

3

Analysis & Remediation (Status: In Progress)

The Issue Owner implements a fix. If the fix requires modifying the overall scope or budget, the issue pauses here and formally triggers the Change Management Process.

4

Validation (Status: Waiting Approval)

The originator or relevant Client Process Owner tests the resolution in the Staging/UAT environment to ensure it meets business requirements.

5

Closure (Status: Resolved)

Formal approval is recorded. For Critical issues, a brief Root Cause Analysis (RCA) is appended to the log to prevent recurrence.

4. Escalation Matrix

If SLA targets are breached, the following automated escalation path applies:

  • 1 Day Overdue: Alert to designated Issue Owner and Project Managers.
  • 3 Days Overdue: Escalated to Joint PM Team & relevant Client Process Owners.
  • 5 Days Overdue: Escalated to Implementation Vendor Operational Leadership.
  • 10+ Days Overdue: Escalated to the Steering Committee / Project Sponsors for executive intervention.

5. Roles & Responsibilities

  • Originator (Key Users): Clearly document the issue with evidence (screenshots, expected vs actual results).
  • Project Managers: Triage, assign, and monitor issue health. Run weekly issue review meetings.
  • Issue Owner: Resolve within SLA, provide daily updates on High/Critical issues.
  • Steering Committee: Unblock resources or make executive decisions for escalated issues.

6. Real-World Implementation Scenarios

Scenario A: Data Migration Mismatch

Issue: During the data migration phase, opening balances provided by the Client Finance team do not map correctly to the new Chart of Accounts.

Action: Logged as High Priority (Functional/Data). Assigned jointly to the Client Finance Lead and the Lead Consultant to resolve mapping logic within 3 days to prevent UAT delays.

Scenario B: Key User Unavailable for UAT

Issue: The primary Procurement Key User is on unexpected leave during the critical UAT week.

Action: Logged as High Priority (Resource). Escalated immediately to the Client Project Sponsor to assign a proxy user to prevent schedule slippage.
